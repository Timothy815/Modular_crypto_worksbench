# Workspace Versioning V1

Last updated: March 27, 2026

Status: Proposed next bounded follow-on after `WORKSPACE-HISTORY-V1`.

## Purpose

This contract defines the first named-version slice for MCW workspaces.

The goal is to let users create intentional restore points they can revisit later, without turning workspace versioning into a full branching VCS or collaborative history system.

## Product Problem

Undo/redo solves recent editing mistakes.

It does not solve longer-horizon authoring needs such as:
- save a known-good round structure before a refactor
- preserve a teaching variant of a workspace
- return to an older checkpoint after several later edits
- compare “before” and “after” at the level of named milestones

Those are versioning problems, not undo problems.

## Core Question

Can MCW let a user create, list, and restore named workspace versions without introducing branching history or a full source-control metaphor?

## Strategic Principle

**Create intentional named checkpoints, not a branching history graph.**

That means:
- versions are explicitly created by the user
- versions belong to one workspace
- restore replaces the current live workspace state with a chosen saved version

This is not:
- automatic version snapshots on every edit
- branching history trees
- merge/conflict workflows
- diff tooling in V1

## First Milestone

The first milestone should answer one clear question:

**Can a user save a named version of a workspace and later restore it reliably?**

## Include

The first slice should likely include:
- one explicit `Save Version` action for the current workspace
- one explicit version list for the current workspace
- restore of a selected named version
- stored snapshot contents that cover:
  - graph
  - layout
  - annotations
  - any relevant workspace-local authored state needed for faithful restore
- user-provided version names
- timestamp metadata

## Exclude

Do not include in V1:
- branching versions
- compare/diff views
- collaborative version history
- auto-save every edit as a named version
- version labels generated by AI
- cross-workspace shared versions
- cloud sync semantics beyond whatever persistence layer MCW already has

## Core Rules

1. **Versions must be explicit**
- a version exists because the user saved it intentionally

2. **Versions must be workspace-local**
- versions belong to one workspace and do not bleed across projects

3. **Restore must be predictable**
- restoring a version replaces the current live workspace state with that saved checkpoint
- V1 does not need partial restore or merge behavior

4. **Versioning must stay distinct from undo/redo**
- versions are named checkpoints
- undo/redo remains the short-horizon recovery system

5. **V1 should prefer clarity over sophistication**
- a simple list of named versions is better than a half-built timeline metaphor

## Recommended Implementation Shape

The strongest V1 shape is likely:
- per-workspace named snapshot list
- snapshot contents aligned with whatever workspace-state shape is already persisted
- simple restore workflow

Reason:
- MCW already serializes workspaces cleanly
- versioning is fundamentally snapshot-oriented in V1
- simplicity matters more than advanced history semantics here

## Expected File Scope

Primary files likely in scope:
- `src/ui/store.ts`
- `src/ui/persistence.ts`
- `src/ui/workbench-document.ts`
- `src/App.tsx`
- small UI surfaces for save/list/restore version actions

This slice should not require engine-layer changes.

## UI Shape

The first UI can be simple.

Good options:
- `Save Version` action in workspace controls
- a per-workspace version list with restore buttons
- optional delete-version behavior later, but not required in V1

The important thing is:
- creating a checkpoint is explicit
- restoring it is obvious
- the system reads like workspace milestone management, not Git

## Success Criteria

This slice is successful when:
- a user can save a named version of a workspace
- a user can see previously saved versions for that workspace
- a user can restore one reliably
- versioning clearly complements undo/redo instead of replacing it

## Validation Expectations

This slice should add focused tests for:
- saving a named version
- listing versions per workspace
- restoring a saved version
- persistence/restore correctness across app reload if applicable
- isolation between versions of different workspaces

## Explicitly Avoid Next

Do not let this become:
- source control by stealth
- automatic branching history
- compare/diff tooling by stealth
- timeline-overhaul UI work

Keep the first move explicit, named, and checkpoint-oriented.
