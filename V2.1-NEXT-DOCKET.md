## Purpose

Record the next ranked priorities after the current ergonomics, rotor, and Python-export-foundations work.

This file exists to keep the project moving without re-litigating near-term order every time a new idea appears.

It is not a replacement for individual implementation contracts.
It is the sequencing surface that says what should come next and why.

---

## Ranked Near-Future Order

### 1. Continue The `v2.1` Builder-Power Line

This remains the best immediate leverage.

Reason:
- MCW already expresses a great deal
- the next bottleneck is still how quickly and confidently a user can build larger machines
- further builder-power work compounds every existing vocabulary and teaching surface

Guiding principle:
- improve assembly speed without hiding structure

Examples of appropriate next builder-power work:
- stronger repeated-stage assembly support
- clearer large-graph authoring flow
- better composite/reuse continuity
- additional explicit authoring leverage where hand-assembly is still too expensive

This remains the immediate active lane.

---

### 2. Expand Python Export Carefully

This is the most strategically important expansion after foundations.

Reason:
- it changes MCW from pure design/simulation into executable specification
- it increases the product’s seriousness without abandoning its teaching value
- each supported new family meaningfully deepens the bridge from visual construction to implementation

Recommended posture:
- expand deliberately
- keep parity first
- prefer clear compatibility boundaries over broad but fragile support

Near-future likely targets:
- additional stateless primitives with high instructional value
- only later, more complex stateful/ticked export lines

---

### 3. Refactor The Largest UI Surfaces

This is the most important maintenance line.

Reason:
- the workbench and inspector are now large enough to become future drag coefficients
- this is not yet an emergency, but it is now a real engineering concern
- postponing indefinitely would make the next feature waves slower and riskier

Primary concern:
- especially `parameter-inspector.tsx`

Goal:
- split large surfaces into cleaner family-oriented or concern-oriented subcomponents
- preserve behavior while reducing future implementation friction

This should be treated as architecture protection, not as a cosmetic cleanup.

## Current Recommendation

The project should proceed in this order:

1. choose the next bounded product-facing slice from the remaining unshipped contracts
2. keep builder-power work selective and explicit where assembly cost is still genuinely high
3. continue Python export expansion carefully where parity remains strategically valuable
4. keep UI refactors scoped as architecture protection rather than drifting into a long maintenance-only phase

The older recommendation order in this file should now be read as historical context, not as a strict live queue. The actual project state has moved forward materially since that note was first written.

Practical near-term posture:
- treat `IMPLEMENTATION-STATUS.md` as the canonical shipped/unshipped surface
- use this docket only to preserve the broader priority shape:
  - bounded builder-power / usability
  - careful Python export deepening
  - selective refactors where large surfaces are becoming a drag coefficient

The docket also now explicitly records one later Python-export architecture refinement:
- `PYTHON-EXPORT-RUNTIME-LIBRARY-V1.md`
- a future deliberate split between reusable runtime library code and separate generated workspace implementation code
- intentionally deferred until after the current export-completeness line reaches a stable milestone

## Non-Goals

This docket should not be used to:
- replace individual implementation contracts
- flatten all future work into one giant roadmap
- justify random priority changes without a better reason than novelty

If a different next move is chosen later, it should be justified against this ordering.

## Exit Condition

This docket is successful when:
- the near-future order is explicit
- multi-window workspace support is recorded as fully shipped
- builder power and Python export remain the primary active priorities
- future sequencing can resume from this point without ambiguity
- a new agent can immediately tell that the older builder-power queue is mostly already complete and that the current question is which bounded next slice is actually highest leverage
