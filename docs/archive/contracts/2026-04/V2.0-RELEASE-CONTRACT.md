# V2.0 Release Contract

Last updated: March 27, 2026

Status: Completed release-framing contract. No final pre-`v2.0.0` product blocker was found.

## Purpose

This contract defines the bounded work required to declare and frame `v2.0` for MCW.

The goal is not to reopen the roadmap.
The goal is to turn the readiness decision into a clear major-version release boundary.

## Why Now

`V2.0-READINESS-AUDIT.md` concluded that MCW is now ready for `v2.0` framing.

That conclusion was based on the recent cohesion arc:
- learning-path reorganization
- selector/pathfinding polish
- primitive-palette coherence
- large-workspace orientation support

Those slices established the product shape that `v2.0` is supposed to recognize.

## Core Decision

`v2.0` should be framed as:
- the release where MCW becomes a coherent **cryptographic systems IDE**
- not because of one new primitive family
- not because of a rewrite
- but because the product’s machine language, teaching surface, and workbench experience now align well enough to form one intentional whole

## Scope

This contract is limited to:
- defining the official meaning of `v2.0`
- defining the release framing and positioning
- deciding whether one tiny final polish item is needed before tagging
- updating the repo’s status and handoff docs to reflect the `v2.0` boundary

This contract may include:
- a short release narrative
- updated milestone/status docs
- a final tag recommendation path

This contract may also include:
- one tiny final polish item only if it is clearly release-framing critical

## Non-Goals

Do not use this contract to:
- reopen the whole roadmap
- add a new cryptographic family by default
- redesign the workbench
- perform broad cleanup just because a major version is being declared
- smuggle in a large deferred feature as “release prep”

## Required Behaviors

1. **Define `v2.0` explicitly**
- the contract must state what `v2.0` means in product terms

2. **Keep the release boundary honest**
- `v2.0` should describe the coherent form MCW has reached, not invent a false revolution

3. **Keep release prep bounded**
- if a final polish item is included, it must be:
  - small
  - release-critical
  - singular

4. **Avoid semantic drift**
- do not let `v2.0` become a catch-all for “more advanced features later”

5. **Preserve continuity**
- update the repo context so future sessions understand that `v2.0` is the active release boundary

## Success Criteria

This contract is successful when:
- it states clearly what `v2.0` stands for
- it gives the project a clean major-version narrative
- it identifies whether a final tiny polish step is required
- it leaves the repo ready for a deliberate `v2.0` tag rather than indefinite late-`v1.x` drift

## Suggested Validation Questions

Before finalizing the release framing, ask:
- does the proposed `v2.0` meaning accurately match the shipped product?
- would a user or collaborator understand why this is a major version?
- is there any remaining mismatch serious enough to make immediate tagging feel premature?
- if so, is that mismatch small enough to fix in one bounded pre-release step?

## Likely Deliverables

The output of this contract should likely include:
- `V2.0-RELEASE-NOTES.md`
- updates to:
  - `IMPLEMENTATION-STATUS.md`
  - `README.md`
  - `CLAUDE.md`

If no final polish is required, this contract should end with:
- a recommendation to tag `v2.0.0`

If one final polish item is required, this contract should end with:
- one bounded pre-`v2.0.0` implementation slice
- and nothing broader

## Relationship To Recent Work

This contract follows:
- `V2.0-READINESS.md`
- `V2.0-READINESS-AUDIT.md`
- the full post-`v1.44.0` cohesion arc

Those slices answered whether MCW is ready.
This slice defines how to declare that readiness cleanly.

## Likely Outcome

If the readiness result holds, this contract should become the immediate bridge to:
- `v2.0.0`

The point is to make the major-version transition explicit, bounded, and honest.
