# Point Order and Subgroups V1

Last updated: May 2, 2026
Status: Shipped

## Purpose

Add the next honest ECC teaching layer for MCW so students can see that elliptic-curve points do not all behave identically: points have finite order, repeated point action can cycle back to infinity, and subgroup structure matters to the protocol story.

It is not a signature contract.
It is not a named-curve contract.
It is not a real-world subgroup-attack simulator.

It is the first bounded slice that explains why `nP = ∞` is not a curiosity but a structural fact students need in order to understand ECC honestly.

This slice inherits the shipped `ec-point` provenance model from:

- [Elliptic-Curve Point Mechanics V1](/Users/timothykoerner/Desktop/modular_cryptography/docs/live/contracts/2026-05/ELLIPTIC-CURVE-POINT-MECHANICS-V1.md)

That means incoming point-domain signals already carry explicit curve provenance, and cross-curve mismatch detection is expected to reuse that shipped mechanism rather than invent a new one here.

## Problem

MCW now lets students see:

- points on a visible pedagogical curve
- point addition, negation, doubling
- scalar multiplication
- visible ECDH with shared-point equality

That is enough to show the protocol shape.

It is not yet enough to explain some of the most important structural facts behind that shape:

- a point does not generate the whole curve by default
- repeated point action eventually cycles
- the point at infinity is the identity, not just a special error case
- the order of the chosen base point matters

Without this slice, visible ECDH can still read like “both sides agree by magic repeated multiplication” instead of “both sides are operating inside a finite cyclic subgroup generated by one point.”

## Goal

Add one bounded teaching layer that makes point order and subgroup behavior visible enough for students to explain:

- what point order means
- why `nP = ∞` for the point order `n`
- why different points can have different orders
- why the choice of base point matters to later ECC protocol stories

The result should be:

- one clear order-focused teaching path
- one bounded way to inspect or compute point order
- one visible demonstration that scalar multiplication eventually returns to infinity
- explicit wording about what subgroup observations do and do not prove

## Scope

In scope:

- one bounded order/subgroup primitive or analysis surface
- one flagship demo workspace
- one tutorial
- one repair or interpretation challenge
- micro demos for any new primitive introduced in this slice
- explicit product wording that connects point order to visible ECDH without overclaiming

Out of scope:

- named real-world curves
- cofactor-clearing APIs
- invalid-curve attack simulation as a full red-team lab
- signatures
- protocol wrappers
- automatic secure-base-point selection
- production subgroup validation claims

## Required Product Behavior

1. A student must be able to see that repeated scalar action on one point eventually cycles back to infinity.
2. A student must be able to distinguish “the curve” from “the subgroup generated by this point.”
3. The product must make clear that point order is a structural property of a chosen point on a chosen curve, not a generic property of all points.
4. The product must say clearly that observing point order on a tiny pedagogical curve is not the same thing as evaluating a production-safe generator choice.
5. The slice must strengthen understanding of visible ECDH rather than replace it with a new black-box fact.

## Recommended V1 Shape

V1 should prefer one bounded order-oriented surface over a broad attack or standards story.

Recommended path:

- add one narrow helper such as `PointOrder`
- or add one bounded order-analysis surface tied to an explicit point input
- then build the teaching path around visible verification that `nP = ∞`

Do not turn this into:

- a full curve census tool
- a named-curve comparison table
- a generalized security scoreboard

Why:

- the educational value comes from one visible repeated-point cycle
- too much surface area will blur the subgroup concept before students own it

## Primitive Strategy

V1 may add one narrow helper if needed.

Preferred helper:

- `PointOrder`

Recommended shape:

- inputs:
  - one `ec-point`
- output:
  - one `integer`
- explicit params:
  - `p`
  - `a`
  - `b`
- behavior:
  - returns the smallest positive integer `n` such that `nP = ∞`
  - fails visibly on invalid point input or cross-curve mismatch
  - produces a distinct visible “order exceeds observable regime” result if V1’s bounded search regime is exceeded

Acceptable alternative:

- an analyze-tab order surface with no new primitive, if it is still explicit enough to wire into the teaching story

Unacceptable V1 helpers:

- `SecureGenerator`
- `ChooseBasePoint`
- `SafeCurve`
- any helper that turns subgroup reasoning into a hidden certification step

## Domain Semantics

### Point order

In V1, point order means:

- the smallest positive integer `n` such that `nP = ∞`

It does not mean:

- the size of the whole curve
- a claim that the point is suitable for production use
- a hidden “security score”

### Subgroup language

The product should say plainly:

- repeated scalar action from one point generates a subgroup
- different starting points can generate different subgroups
- visible ECDH works inside the subgroup generated by the chosen base point

It must also say plainly:

- this pedagogical slice is about structure and intuition
- it is not a substitute for real parameter-validation rules

## Engine Requirements

### 1. Honest finite order behavior

If V1 adds `PointOrder`, it must compute the smallest positive `n` such that `nP = ∞`.

It must not:

- stop at the first arbitrary repeat limit and call that the order
- silently approximate
- silently coerce malformed points

### 2. Explicit infinity connection

The teaching path must make the relationship between:

- scalar multiplication
- point order
- visible infinity

explicit and inspectable.

Students should be able to verify at least one statement like:

- `order(P) * P = ∞`

inside the workbench.

### 3. Explicit curve consistency

Like the rest of the point family, any order surface must verify:

- incoming point carries curve provenance
- point belongs to the declared curve
- cross-curve mismatches fail explicitly

### 4. Bounded computational regime

V1 should stay honest about the pedagogical regime.

That means:

- tiny explicit curves
- bounded search for point order if implemented directly
- an explicit visible order-search budget exposed in the product surface before execution
- a distinct visible “too large to observe in this workbench” outcome if the order search would exceed the V1 pedagogical budget

Do not imply that V1 order analysis scales to real deployment curves.

Recommended V1 shape:

- use one fixed product constant for the maximum order-search budget
- surface that bound in module detail or inspector copy
- do not make the search limit a casual author-facing tuning knob in V1

Why:

- the teaching point is that the workbench has an observation budget, not that students should tune search heuristics blindly
- “too large to observe here” is more honest and educational than a generic runtime failure

## Validation Requirements

V1 must validate at least:

- point input is a valid `ec-point`
- curve params satisfy the shipped curve rules
- runtime cross-curve mismatch is rejected
- any order-search bound is explicit and visible when exceeded

If a new primitive is added, validation should distinguish:

- invalid point input
- invalid curve parameters
- cross-curve mismatch
- bounded-search regime exceeded / order too large to observe

## UI Requirements

### 1. Order must read as a point property

The product surface must make clear that order belongs to:

- this point
- on this curve

not to ECC in general.

This is required in the inspector/consequence copy for the order result itself, not only in library text.

### 2. Infinity must remain explicit

If the flagship teaching path verifies `nP = ∞`, the infinity result must remain visibly rendered as infinity.

Do not hide it behind:

- blank output
- null
- omitted sink values

### 3. What this does not prove

At minimum, library/detail copy and the tutorial must say:

- observing a point’s order on a tiny pedagogical curve does not prove production-safe generator quality
- subgroup understanding helps explain ECC structure, but it is not a full deployment-validation story

## Teaching Requirements

V1 must ship:

- one main demo
- one tutorial
- one challenge

### Flagship demo

The flagship demo should show at least:

- one visible base point `P`
- one visible order result `n`
- one visible verification path that checks `nP = ∞`
- one contrasting point or branch that helps show different points can behave differently

### Tutorial

The tutorial must walk through:

1. what point order means
2. why repeated scalar action eventually cycles
3. why infinity is the identity result, not a crash
4. how this clarifies the base-point choice in visible ECDH

That fourth step must conclude plainly:

- visible ECDH depends on choosing a base point whose order is large enough to avoid trivial tiny cycles
- MCW’s tiny pedagogical curves make that structural dependence visible
- this does not mean MCW is evaluating production-safe base points

### Challenge

The challenge should be a broken-workspace repair or interpretation task such as:

- a wrong claimed order
- a broken `nP = ∞` verification leg
- a point-choice mixup that causes the expected order story to fail

### Micro demos

If V1 introduces a new primitive like `PointOrder`, it must ship with a primitive micro demo.

This slice should also ship both protocol-adjacent micro demos:

- visible verification that `nP = ∞`
- and a comparison showing two points with different orders on the same pedagogical curve

## Python Export

Python export parity is not the main goal of this slice.

If V1 introduces a new primitive like `PointOrder`, parity for that primitive is expected if it can be added through the already-shipped point/scalar surface without materially widening the slice.

If parity would require a broader point-family export expansion, record that explicitly and split it into:

- `ECC-POINT-PYTHON-EXPORT-PARITY-V1`

Do not hand-wave parity debt as “close enough.”

## Non-Goals

This slice must not:

- imply real-world ECC parameter vetting
- imply that subgroup understanding alone makes the protocol safe
- collapse subgroup choice into one “good/bad” verdict
- introduce named-curve marketing or standards framing
- drift into signatures

## Acceptance Criteria

V1 is complete when:

1. MCW can show at least one honest visible point-order teaching path.
2. Students can verify a statement like `nP = ∞` in-product.
3. The product distinguishes the subgroup generated by a point from the whole curve clearly enough for tutorial use.
4. Infinity remains explicit and legible in the verification path.
5. Manual/demo/tutorial/challenge coverage ships with the slice.
6. The product states clearly what subgroup observations do and do not prove.
