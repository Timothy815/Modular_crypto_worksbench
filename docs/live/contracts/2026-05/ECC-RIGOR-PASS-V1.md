It is not a new primitive contract.
It is not a named-curve contract.
It is not a signature contract.

It is an honesty-and-interpretation contract.

This contract confirms that `PointEquals` is already a shipped primitive in MCW's ECC line:

- it emits a one-bit `bits` output
- it is already used as the visible equality surface in the shipped ECDH slice
- this pass tightens its framing only; it does not introduce it

## Problem

MCW now ships a real ECC teaching line:

- visible point construction and validation
- visible point negation, addition, and doubling
- visible scalar multiplication
- visible ECDH
- visible point order and subgroup examples

That is enough capability to teach real structural ideas.

It is also enough capability for the product to be misread if its wording drifts.

The main risks are:

1. students may generalize from a small visible pedagogical curve to real deployment curves
2. students may confuse "private" with "secret from everyone in the current workspace"
3. students may treat shared-point equality as "finished encryption"
4. students may overread point order or subgroup observations as direct production-safe parameter evaluation
5. students may mistake visible structural demonstrations for security certification

MCW should teach those boundaries explicitly, not rely on the instructor to repair them after the fact.

## Required Product Behavior

### 1. Every shipped ECC surface must distinguish structure from deployment claims

At minimum, the shipped ECC surfaces must clearly separate:

- what this graph shows structurally
- what this does not prove about production ECC

This distinction should appear in the most-read product surfaces, not only in hidden docs.

### 2. The product must say plainly that current ECC slices are pedagogical

The product should explicitly say that current ECC workspaces use:

- small visible pedagogical curves
- visible values for inspection
- bounded observation budgets where applicable

The product must not imply that these workspaces are real-world curve-selection or deployment tools.

### 3. Private/public/shared language must stay pedagogically honest

When MCW uses words like:

- private scalar
- public point
- shared point

the surrounding copy must explain the modeling choice:

- values are kept visible on purpose so students can inspect the algebra
- that visibility is not meant to simulate operational secrecy

### 4. Shared-point success must not read like finished key agreement

The visible ECDH flow must keep saying:

- both sides land on the same visible shared point
- that shared point is not yet a finished symmetric key
- real systems still derive usable key material with additional steps outside the current slice

### 5. Point order and subgroup wording must stay local

Point order copy must stay local in scope:

- the order belongs to this point on this curve
- the subgroup is generated by repeated action from that chosen point
- a small visible order is structurally informative here
- it is not by itself a generic indictment or certification of "ECC"

## Scope

## Canonical Language

This pass should reuse these short forms consistently unless a surface requires a small variation for readability:

1. `visible pedagogical curve`
2. `repeated point action`
3. `shared point, not finished key`
4. `point-local subgroup structure, not deployment validation`

These are not slogans. They are the canonical phrasing anchors that future ECC-facing copy should align to.

## Placement Priority

When a required boundary can only be placed in some surfaces, the priority order is:

1. inspector/consequence copy
2. demo/tutorial copy
3. library detail copy
4. manual reference copy

This means:

- the inspector is the primary interpretation surface
- tutorial prose is secondary reinforcement
- library and manual text should align, not carry the whole burden alone

## UI Requirements

### 1. Inspector/consequence copy is mandatory for the highest-risk interpretations

At minimum, these shipped transformation views need bounded explanatory copy:

- `ScalarMultiply`
- `PointEquals`
- `PointOrder`

Those views should answer:

- what the current result means
- what it does not prove

Minimum anchors:

- `ScalarMultiply`
  - must say this is `repeated point action`
  - must say it is not coordinate multiplication
  - must say a visible result on a small pedagogical curve does not imply production-safe ECC
- `PointEquals`
  - must say both paths land on the same visible point on the same curve
  - must say equality here verifies a structural meeting point
  - must say this is `shared point, not finished key` when used in the visible ECDH line
- `PointOrder`
  - must say the order belongs to this point on this curve
  - must say the subgroup is generated by repeated action from this chosen point
  - must say small visible orders clarify structure but do not validate deployment safety

### 2. Demo and tutorial summaries must carry the right framing

The ECC demos and tutorials should not read like:

- "here is real ECC"
- "this proves the curve is strong"
- "this is a finished secure exchange"

They should read like:

- "here is the visible algebraic structure"
- "here is why this matters to the protocol story"
- "here is what still lies outside this slice"

Minimum anchors:

- the visible ECDH demo/tutorial must say values remain visible on purpose for learning
- the visible ECDH demo/tutorial must say the outcome is a `shared point, not finished key`
- the point-order demo/tutorial must say this is `point-local subgroup structure, not deployment validation`

### 3. Manual and library entries must align with the same bounded language

The manual and module library should not say something weaker or stronger than the inspector.

The same concepts should repeat consistently:

- visible pedagogical curve
- repeated point action
- shared point versus finished key
- subgroup structure versus deployment safety

At minimum:

- `ScalarMultiply`, `PointEquals`, and `PointOrder` library/manual entries should reuse the canonical short forms
- the ECC module family entries should not imply real-world curve evaluation, secure deployment, or finished protocol completeness

## Teaching Requirements

### 1. The ECDH tutorial must keep the key-boundary explicit

The visible ECDH tutorial should keep or strengthen the line that:

- both sides agree on a shared point
- the shared point is not yet a finished symmetric key

This boundary must also appear in the shared-result inspector/consequence path, not only in tutorial prose.

### 2. The point-order tutorial must keep the subgroup-security connection bounded

The point-order tutorial should say plainly:

- small-order visible points clarify why base-point choice matters
- MCW is showing the structural reason
- MCW is not performing production-safe curve or generator validation

### 3. Challenge copy should reinforce the intended mental model

Repair challenges in the ECC line should refer to:

- shared-point equality
- repeated point action
- point-specific order

They should avoid black-box language like "fix the crypto" or "restore security."

Good register examples:

- "restore the shared-point equality path"
- "repair the repeated point action branch"
- "restore the point-specific order check"

Bad register examples:

- "fix the crypto"
- "restore security"
- "make the ECC safe again"
