# Scalar Multiplication V1

Last updated: May 2, 2026
Status: Shipped

## Purpose

Add the first honest scalar-multiplication layer for MCW so the workbench can show repeated group action over visible elliptic-curve points without jumping prematurely to ECDH or signature shells.

It is not an ECDH contract.
It is not a signature contract.
It is not a named-curve catalog contract.

It is the repeated-point-action layer required before those can be honest.

## Problem

MCW now has:

- an exact integer substrate
- a visible `integer` signal domain
- real prime-field arithmetic
- a visible `ec-point` signal domain
- visible point construction, negation, addition, doubling, and infinity handling

That is enough to teach:

- point membership
- additive inverse
- point addition
- doubling as a special formula branch

It is not enough to teach why ECC public keys are generated by repeated point action rather than by one-off point addition.

Without scalar multiplication, future ECC work would be pushed toward one of two bad outcomes:

- hiding repeated point action inside opaque protocol modules
- pretending ECDH or signatures are understandable before the repeated group action itself is visible

Both would violate MCW's product standard.

## Goal

Add one bounded scalar-multiplication primitive with visible scalar and point inputs, visible point output, explicit handling of `0`, `1`, and infinity, and enough teaching/demo support that students can see repeated point action directly.

The result should be:

- one clearly named scalar-multiplication primitive
- explicit visible scalar input
- visible point output
- honest runtime behavior for edge cases
- Python export parity for `ScalarMultiply` itself, without silently absorbing unrelated deferred export debt
- demo and micro-demo coverage that makes the primitive teachable in isolation

## Scope

V1 is intentionally narrow.

In scope:

- one visible scalar-multiplication primitive, such as `ScalarMultiply`
- integer-domain scalar input
- `ec-point` input and output
- explicit visible handling for:
  - scalar `0`
  - scalar `1`
  - infinity input
  - cross-curve mismatch
- bounded inspector/readout support for scalar-multiplication results
- Python export parity for `ScalarMultiply`
- one main demo workspace
- micro demos for each newly introduced primitive in this slice
- one tutorial

Out of scope:

- ECDH
- signatures
- scalar multiplication over binary-field curves
- named curve catalogs
- multi-scalar tricks or windowing algorithms as separate teaching surfaces
- protocol wrappers

## Required Product Behavior

1. A student must be able to tell that scalar multiplication is repeated point action, not integer multiplication on coordinates.
2. Scalar input must remain visible and explicit.
3. The result must remain a visible `ec-point`, not a hidden tuple or text blob.
4. Edge cases must be handled honestly rather than silently coerced.
5. The product must not imply that scalar multiplication means “ECC support is done.”

## Recommended V1 Shape

V1 should add exactly one new point/scalar operator:

- `ScalarMultiply`

Do not combine:

- scalar multiplication
- ECDH
- protocol narratives

in one slice.

Why:

- scalar multiplication is already a meaningful new cognitive layer
- it introduces algorithmic repetition and larger trace consequences
- students need this one stable step before any public-key protocol story is added

## Required Primitive Family

V1 should add:

- `ScalarMultiply`

It should read clearly as repeated point action, not as generic multiplication.

### ScalarMultiply

Recommended path:

- inputs:
  - one `integer` scalar input
  - one `ec-point` point input
- output:
  - one `ec-point`
- explicit curve params remain visible on the receiving primitive in V1:
  - `p`
  - `a`
  - `b`

The primitive should be implemented as honest repeated point action over the shipped point mechanics, not as a coordinate shortcut that hides the group operation.

## Domain Semantics

### Scalar input

In V1, the scalar should mean:

- an exact non-negative integer in the supported product regime

It should not mean:

- signed scalars
- implicit modular reduction by hidden subgroup order
- a secret key abstraction

V1 does not require hidden reduction by subgroup order or an author-facing subgroup-order parameter.
Large-but-valid scalars within the safe-integer regime may still be computed exactly, but MCW should frame the point/curve surface as pedagogically small rather than imply that arbitrarily large scalar choices are meaningful as a real-world parameter story.

V1 scalar semantics should stay deliberately plain.

### Point output

The output should remain:

- a visible `ec-point`

That includes:

- affine point results
- visible infinity where mathematically correct

## Engine Requirements

### 1. Honest repeated point action

Scalar multiplication must be computed through exact repeated point action over the shipped point mechanics.

It must not:

- fake the result through precomputed tables hidden from the product model
- coerce the point domain into anonymous coordinate arrays
- hide cross-curve inconsistencies

An efficient double-and-add implementation is acceptable as long as the behavior remains mathematically faithful and the product does not imply a different operation than it is actually performing.

V1 does not need to expose every intermediate double-and-add step as a first-class execution trace surface.
But it must not leave the operation feeling like a black box:

- the module's inspector or consequence copy must explicitly explain that the result is produced by repeated point addition and doubling on the same curve
- the tutorial and micro demos must make that repeated-action meaning visible through comparison, not just through a final output value

### 2. Visible scalar and point I/O

`ScalarMultiply` must consume:

- one `integer`
- one `ec-point`

and emit:

- one `ec-point`

Do not fold scalar authoring into module params in V1.
The scalar must be a visible signal.

### 3. Explicit curve consistency

Like the point-mechanics slice, scalar multiplication must verify that:

- the incoming point carries curve provenance
- that provenance matches the primitive's declared `p`, `a`, and `b`

Cross-curve mismatches must fail explicitly.

### 4. Honest edge cases

V1 must define at least:

- `0 * P = ∞`
- `1 * P = P`
- `k * ∞ = ∞` for visible non-negative scalars

Undefined or unsupported cases should fail visibly only when the input itself is invalid or outside the declared regime.

### 5. Bounded exactness regime

The scalar and curve params remain bounded by the current exact substrate and safe-integer product surface in V1.

MCW should say this honestly.
This slice is for pedagogically visible scalar action, not real-world large-curve performance or coverage.

## Validation Requirements

V1 must validate at least:

- scalar input is a structurally valid `integer` signal
- curve params are valid under the shipped point-mechanics rules
- point input is valid for the declared curve
- runtime cross-curve mismatches are rejected

Static validation should remain for:

- curve params
- discriminant
- exactness boundary

Runtime validation should remain for:

- malformed point input
- cross-curve mismatch

Validation should distinguish:

- invalid scalar input
- invalid curve parameters
- invalid point input
- cross-curve mismatch
- out-of-regime exactness boundary

## UI Requirements

### 1. Scalar/action readability

Selected scalar-multiplication results must render clearly in the inspector.

At minimum, V1 should support:

- scalar display through the existing integer inspector surface
- point result display through the existing point inspector surface
- a bounded explanation that the operation is repeated point action on the same curve

### 2. Sink honesty

If a scalar-multiplication result is shown at a sink or output-oriented panel, the UI must keep the visible point-domain labeling already established for `ec-point`.

Do not let a point result masquerade as plain text or integer output.

### 3. Mechanical explanation

Where bounded explanation copy appears, the product should teach:

- scalar multiplication means repeated point addition over a visible curve
- it is foundational for later ECC public-key work
- it does not by itself imply ECDH, signatures, or real-world curve support

At minimum, this limitation should appear in:

- the library/detail copy for the scalar-multiplication primitive
- the inspector or module consequence copy for `ScalarMultiply` itself

## Teaching Requirements

V1 must include:

- one main demo workspace
- one tutorial

Recommended main demo path:

1. start from one visible pedagogical point on a small curve
2. multiply it by `2`
3. compare the result with visible `PointDouble`
4. multiply it by `0`
5. inspect visible infinity
6. multiply it by `1`
7. inspect that the original point is preserved

### Micro-demo requirement

Every new primitive introduced in this slice must ship with at least one micro demo in addition to the main demo.

For `ScalarMultiply`, V1 should include at least:

- one `Scalar × 2` micro demo
- one `Scalar × 0` micro demo
- one small nontrivial scalar micro demo such as `Scalar × 3`

The nontrivial scalar micro demo should not stop at a single final point.
It should also make visible a bounded verification path such as:

- `3P = 2P + P`

so the student can see repeated action rather than infer a hidden lookup.

This is not optional polish.
In MCW, a primitive is not fully real until it has a minimal isolated demonstration path.

Challenge content is optional in this slice.

## Python Export Requirements

V1 should include Python export parity for:

- `ScalarMultiply`

Parity means:

- exported Python computes the same point results
- the same visible infinity cases are represented honestly
- cross-curve mismatch and invalid-input failures do not silently degrade in export

Deferred Python export work for previously shipped point-mechanics primitives should be handled in an explicit follow-on export tranche rather than silently folded into this slice.

This contract should not be used to absorb broad point-family export debt under the label of scalar-multiplication parity.

## Non-Goals

V1 should not:

- add ECDH
- add signatures
- add named curve catalogs
- add secret/public key shells
- add point-compression workflows
- imply real-world curve coverage or performance

This is a foundation slice, not a prestige shortcut.

## Success Criteria

V1 is successful if:

1. MCW has a clearly named visible scalar-multiplication primitive.
2. Scalar input remains explicit and point output remains explicit.
3. `0`, `1`, and infinity cases are handled honestly.
4. A student can compare `Scalar × 2` with `PointDouble` and see that they match.
5. A student can inspect `Scalar × 3` and verify a bounded repeated-action identity such as `3P = 2P + P`.
6. Python export remains behaviorally aligned for `ScalarMultiply` itself without widening the slice into a generic point-export catch-up project.
7. The primitive family ships with both a main demo and micro demos, not just implementation coverage.
