# V2.1 Authoring Power Plan

Last updated: March 27, 2026

Status: Active post-`v2.0.0` planning document. First bounded slice implemented on `feature/repeated-structure-authoring`; second bounded cluster-operations follow-on now active.

## Purpose

This plan defines the first post-`v2.0` product direction:
- make MCW more powerful to **author with**
- without weakening its explicit-machine philosophy

The goal is not to add more vocabulary by default.
The goal is to reduce the amount of manual hand assembly required to build complex explicit machines.

## Core Problem

MCW can already express complex repeated structure well.
The authoring bottleneck is that building those structures is still more manual than it should be.

That friction appears in:
- repeated-structure authoring
- composite / iterator ergonomics
- explicit multi-stage machine assembly

In plain terms:
- the machine language is strong
- the builder leverage over that language is still lower than it should be

## Product Goal

Post-`v2.0`, MCW should become:
- more powerful to compose with
- faster to iterate in
- less laborious for repeated structure

But it must stay:
- explicit
- inspectable
- honest about structure

That means:
- accelerate authoring
- do **not** hide the machine

## Strategic Principle

**Reduce repeated hand assembly without replacing explicit structure with magic.**

Good post-`v2.0` authoring power:
- duplicate or reshape visible structure faster
- expose meaningful reusable controls cleanly
- make repeated machine patterns easier to assemble and inspect

Bad post-`v2.0` authoring power:
- hidden auto-generation that obscures what was built
- “wizard” flows that bypass graph understanding
- abstractions that make the machine less legible

## Three Main Lanes

### 1. Repeated-Structure Authoring

This lane exists to reduce the cost of building visible repeated patterns.

Examples:
- duplicate a selected cluster inside the same workspace
- preserve internal topology while remapping IDs safely
- place the duplicate with a readable offset
- make it practical to build stage-2 / stage-3 / receiver-side mirrors without rewiring everything by hand

This is the strongest immediate authoring-power lane because it improves:
- explicit repeated rounds
- mirrored encrypt/decrypt flows
- sender/receiver structures
- multi-stage comparison machines

### 2. Composite / Iterator Ergonomics

This lane exists to make reusable architecture modules more flexible without turning them into black boxes.

Examples:
- clearer promotion from visible selection into reusable architecture
- stronger duplicate-as-custom workflows for built-in reusable modules
- better outer-shell exposed controls where forwarding is already justified
- better editing continuity between the canvas, reusable object, and custom duplicate

This is high value, but it should build on the current composition model rather than reopen it.

### 3. Authoring Acceleration For Explicit Multi-Stage Machines

This lane exists to make larger staged machines easier to assemble and maintain as visible systems.

Examples:
- stage-aware layout support
- stronger lane or phase structure for repeated machines
- easier handling of visible key buses, split/join patterns, and side-by-side role separation

This is important, but it should come after the first repeated-structure acceleration win unless a stronger bottleneck appears.

## Recommended Order

### First Recommended Slice

**`V2.1.0` should begin with repeated-structure authoring.**

Reason:
- it is the clearest current builder bottleneck
- it improves complex-machine construction directly
- it strengthens both freeform workbench authoring and later reusable-architecture workflows
- it can stay explicit and local

### Second Likely Slice

After that:
- selected cluster operations

Reason:
- once repeated visible structures are easier to build, the next leverage point is selecting and removing visible fragments with the same level of authoring leverage

Concrete next contract:
- `SELECTED-CLUSTER-OPERATIONS-V1.md`

### Third Likely Slice

After that:
- composite / iterator ergonomics

Reason:
- once repeated visible structures are easier to build and edit, the next leverage point becomes packaging and tuning them more effectively

## Recommended First Contract Shape

The strongest first bounded contract is likely:
- **same-workspace cluster duplication / repeated-structure acceleration**

Primary user story:
- select a working graph fragment
- duplicate it in the same workspace
- keep internal topology and params
- get safe remapped IDs
- continue editing the repeated structure immediately

Why this is strong:
- it directly attacks repeated hand assembly
- it keeps structure visible
- it reuses patterns MCW already established in cross-workspace clipboard and composite capture

This should not become:
- linked clones
- hidden template instances
- global sync between repeated structures
- a stealth macro language

## Existing Foundations To Reuse

MCW already has building blocks that make this line realistic:
- cross-workspace clipboard
- composite capture
- composite unzip
- duplicate-as-custom reusable flow
- parameter forwarding
- workspace landmarks

The post-`v2.0` plan should reuse those foundations rather than invent a parallel authoring system.

## Non-Goals

Do not turn `v2.1` into:
- “add all missing UX conveniences”
- a generic visual-programming feature spree
- hidden code generation
- abstraction-heavy shortcuts that make the graph less meaningful

## Success Criteria

This plan is successful when:
- `v2.1` starts from a clear builder-power problem
- the first slice clearly improves authoring leverage
- complex explicit machines become less laborious to build
- MCW gains speed and flexibility without losing inspectability
