# FLAGSHIP-LAB-CLASSICAL-V1

Status: Implemented

Owner: Codex
Scope: Classical Flagship Sequence / Tutorials / Challenges / Verification / Manual

## Why

MCW is now strong enough that its next differentiator should not be another isolated primitive.

What makes the product special is its ability to teach a whole cryptographic machine as a visible system:
- buildable
- inspectable
- traceable
- repairable
- verifiable
- exportable

The classical rotor line is already one of the product's most distinctive strengths:
- explicit rotor stepping
- ring setting
- turnover
- double-step logic
- return-path realism
- control-bank extensions
- Python export and parity support

But those capabilities still live mostly as separate demos and slices.

The next honest move is to package them into one classroom-ready flagship lab sequence that demonstrates why MCW is different from a static simulator or a black-box cipher explainer.

## Goal

Create one high-impact classical flagship lab sequence that turns the existing rotor / Enigma-style line into a coherent teaching pathway for students and instructors.

The first milestone should make it possible to:
- begin with one canonical classical machine path
- learn rotor mechanics through one staged tutorial sequence
- repair or reason about that system through multiple linked challenges
- verify behavior against explicit expected outputs
- end with one export/parity-oriented capstone handoff

## Product Boundary

This slice is:
- classroom-first
- sequence-first
- built from already-shipped classical machine capabilities
- intended to prove product distinctiveness through depth and coherence

It is not:
- a new rotor primitive line
- a historical museum rewrite
- a full curriculum platform
- a generalized grading engine
- a full “course mode”

The right framing is:
- one polished classical glass-box lab family
- one teachable progression
- one professor-ready showcase

## Required V1 Shape

1. V1 should define one flagship classical lab pathway built from already-shipped demos, tutorials, challenges, verification, and export capabilities.
2. The sequence should be centered on the rotor / Enigma-style line, not split across unrelated historical systems.
3. V1 should include:
   - one canonical entry demo
   - one staged tutorial sequence
   - at least two linked challenges
   - one manual subsection or manual expansion that supports the whole sequence
   - one explicit verification step
   - one explicit export/parity capstone handoff
4. The sequence should explicitly teach:
   - forward rotor substitution
   - inverse return-path behavior
   - position vs ring setting
   - turnover
   - double-step logic
5. The sequence must reference demos, tutorials, and challenges by stable IDs, not by display titles alone.
6. The sequence should remain bounded to already-shipped machine behaviors rather than adding new engine work in V1.
7. The final step should make clear that MCW can carry the machine from authored workspace to exported Python while preserving inspectable behavior.
8. V1 should include demo searchability in the workspace-selection surface so an instructor or student can find flagship labs by terms like `rotor`, `return path`, `double-step`, or `Enigma` without manually browsing groups.
9. Flagship demos, tutorials, and challenges should use explicit lab-style numbering or namespacing so the intended sequence order is unmistakable.
10. The parity capstone should include a short success guide that explains what to do if local Python is unavailable, so environment setup does not erase the teaching value of the sequence.

## Preferred V1 Direction

The likely best first shape is a three-part classical sequence:

1. **Machine Path**
   - start with the explicit rotor return-path machine
   - make the reflector + reverse traversal mechanically legible

2. **Stepping Realism**
   - move into advanced rotor stepping
   - focus on ring setting vs position, turnover, and double-step

3. **Trust And Handoff**
   - verify the machine against expected behavior
   - export to Python
   - run or explain parity as the final trust step

That gives the user a visible classical machine journey:
- structure
- motion
- debugging
- trust

## Sequence Rules

- The sequence should feel like one family, not a list of unrelated labs.
- Each step should have a clear teaching purpose and a visible success condition.
- The challenges should teach repair and explanation, not just random experimentation.
- The sequence should require one explicit trace/analyze moment at the exact turnover or double-step event.
- The export/parity handoff should be framed as “prove the authored machine survived export,” not as an afterthought.
- The sequence should be suitable for an instructor to assign as a bounded classical lab progression.

## Teaching Rules

- The sequence must not treat Enigma-like behavior as magical folklore.
- Every surprising behavior should be explained through visible machine structure:
  - stepping
  - notches
  - gates
  - linked reverse traversal
- The sequence should explicitly distinguish:
  - substitution
  - permutation/path reversal
  - stepping/control
  - verification
  - export trust
- The tutorial and challenge copy should help a student explain *why* the machine behaved as it did, not only restore the correct output.
- One challenge in the sequence should focus specifically on ring setting versus rotor position, since that is a confusion point MCW is uniquely able to expose honestly.

## Non-Goals

- No new rotor primitive in V1
- No full historical accuracy expansion beyond the already-shipped bounded realism line
- No new visualization engine just for this sequence
- No auto-generated instructor grading mode
- No broad multi-family historical curriculum in the same slice

## Success Condition

This slice is successful if:
- a student can complete one coherent classical rotor sequence in MCW
- explain the return path and double-step without appealing to hidden magic
- solve linked repair challenges
- verify behavior against expected results
- and understand that the same machine can then be exported with parity support, with a clear path for either running parity locally or understanding the handoff if Python is not available

## Notes

This should come before adding another experimental classical primitive.

If MCW is going to prove uniqueness to a professor, it needs one unmistakably polished classical flagship path that demonstrates:
- visible machine mechanics
- visible debugging
- visible verification
- visible export trust

The goal is not to have “many historical demos.”
The goal is to have one classical sequence strong enough that a professor can say:
- this tool does something materially different from static lecture slides or a simple cipher toy
